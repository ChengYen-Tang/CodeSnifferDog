## 背景

目標是打造一個面向大型專案的全自動化 Code Review Agent，能在最少人工介入下完成程式碼審查、彙整問題、輸出結果，並作為可擴充的服務能力提供給不同使用方式。

## 目標

- 建立一個幾乎不需要與使用者互動的 Code Review Agent。
- 支援大型專案的自動化程式碼審查流程。
- 提供 CLI 使用模式，讓使用者可在本機或 CI 流程中執行。
- 提供 Server Mode，作為可被 UI 與第三方服務整合的後端能力。
- 採用前後端分離設計，降低耦合並提升整合彈性。
- 以可配置的規則文件驅動不同類型的 Code Review 分析與報告輸出。
- 清楚分離「固定的 Agent Prompt 框架」與「使用者可替換的 Review 規則內容」。
- 提供統一的設定與規則存放機制，供 CLI 與 Server 共用核心運作模式。

## 使用者 / 利害關係人

- 開發者
- 技術主管 / Reviewer
- DevOps / CI 維護者
- 第三方整合方

## 功能需求

### 核心能力

- FR-001 系統應能對大型專案執行自動化 Code Review。
- FR-002 系統應盡可能在低互動或無互動情境下完成主要工作流程。
### 使用模式

- FR-003 系統應提供 CLI 模式，供使用者透過命令列操作。
- FR-004 系統應提供 Server Mode，透過 API 或服務介面提供 Code Review 能力。
- FR-005 Server Mode 應採前後端分離架構設計。
- FR-006 Server Mode 除了官方提供的 UI 外，也應支援第三方系統串接。
### 輸入與輸出

- FR-007 CLI 模式下，使用者應提供專案目錄作為 Code Review 的輸入來源。
- FR-008 Server Mode 下，使用者應可上傳打包為 ZIP 的專案檔案作為 Code Review 的輸入來源。
- FR-009 系統的主要輸出格式應為 Markdown 報告。
- FR-010 CLI 模式下，使用者應可指定報告匯出目錄；若未指定，系統應使用預設輸出位置。
- FR-011 Server Mode 下，系統應提供可由前端 UI 呈現的 Review 結果資料。
- FR-012 Server Mode 下，系統應提供將 Review 結果打包為 ZIP 供使用者下載的能力。
### 規則系統

- FR-013 系統應以規則目錄中存在的 Markdown 規則文件集合作為本次要執行的 Review 規則來源。
- FR-014 系統應提供一個規則文件存放位置，用於管理多個 Markdown 規則文件。
- FR-014A 系統應提供一個設定檔與規則目錄的標準結構，至少包含 `appsettings.json` 與 `rules/` 目錄。
- FR-014B `appsettings.json` 應用於管理系統設定，例如推理提供商與相關執行參數；具體欄位可於設計與實作階段依需要補充。
- FR-014C `rules/` 目錄應用於存放各類 Markdown 規則文件。
- FR-015 每個 Markdown 規則文件應代表一類獨立的 Review 規則或分析主題，例如記憶體洩漏、效能或其他檢查面向。
- FR-016 系統應能根據規則目錄中的 Markdown 規則文件執行相應的分析，並產生對應的報告內容。
- FR-017 系統應支援由多個規則文件組合成一次 Review 任務。
- FR-017A Review Agent 應使用固定的 System Prompt 框架，並將使用者選取的規則內容插入預先定義的佔位區塊中。
- FR-017B 使用者可替換或新增規則文件內容，但不直接編輯核心的 System Prompt 框架。
- FR-017C 規則文件在第一版應以簡單、可由使用者直接編輯的 Markdown 內容為主，優先採條列式規則表達。
- FR-018 當規則目錄中存在多個規則文件時，系統應可為不同規則類型分派獨立的子任務或子代理程序並行執行分析。
- FR-019 每個被選取的規則文件應產生對應的獨立報告，例如 `記憶體洩漏-report`、`性能-report`。
- FR-020 系統可在個別規則報告之外，進一步提供整體彙整報告，但此能力屬於後續可擴充項目。
- FR-021 若規則目錄中存在多個規則文件，系統應自動對每個規則文件建立相對應的 Review 子任務，無需使用者在執行時逐一選取。
- FR-022 若使用者不希望執行某類檢查，應透過修改對應規則文件內容或移除該規則文件達成，而非在執行階段以互動方式選取。
### 設定與部署

- FR-023 CLI 與 Server Mode 應皆依賴設定檔與規則目錄運作，以維持一致的配置方式。
- FR-024 Server Mode 下，設定檔與規則目錄應預設部署於應用程式子目錄中的固定位置。
- FR-025 CLI 模式下，設定檔與規則目錄應可存放於使用者家目錄下的專用資料夾中。
- FR-026 CLI 模式下，除了預設的使用者家目錄設定位置外，系統亦應允許透過參數或環境變數覆寫設定根目錄。
- FR-026A CLI 模式應提供初始化參數，可自動在預設的使用者家目錄設定位置建立設定檔、目錄結構與規則範本。
- FR-027 系統應支援採用 OpenAI 相容協定的推理提供商設定，至少包含 OpenAI、Azure OpenAI 與本地部署提供商。
- FR-028 本地部署提供商應至少涵蓋 `vllm`、`sglang` 與其他 OpenAI 相容 LLM 服務。
### 資料保留與清理

- FR-029 CLI 模式下，任務完成後應僅保留最終報告，不保留中間分析產物。
- FR-030 Server Mode 下，使用者上傳的 ZIP 檔與解壓後專案內容應於分析完成後刪除。
- FR-031 Server Mode 下，報告下載檔應於使用者發出請求時，根據資料庫中的結果動態匯出為 ZIP。
- FR-032 Server Mode 下，為支援 UI 同步、檢視與複查，分析過程與結果資料應保留於資料庫中，直到使用者主動刪除。
- FR-033 CLI 模式下，任務失敗後不要求保留可供後續複查的任務資料。
### 任務處理與可觀測性

- FR-034 Server Mode 應支援以 worker 機制處理 Review 任務，且 worker 數量可由設定檔配置。
- FR-035 每個 worker 在同一時間應僅處理一個 project。
- FR-036 每個 worker 應可設定其下允許的最大平行 Agent 數量。
- FR-037 當可用 worker 已滿時，新進 project 應進入 queue 等待處理。
- FR-038 系統應可設定可同時存在的 project 上限，範圍包含處理中與 queue 中的 project 總數。
- FR-039 使用者應可在任務尚未完成前主動刪除 project。
- FR-040 Server Mode 應提供 task 狀態，至少包含 `queued`、`reviewing`、`completed`、`failed` 與 `canceled`。
- FR-041 CLI 與 Server Mode 都應能顯示目前執行階段與進度資訊。
- FR-042 CLI 與 Server Mode 都應能記錄並提供本次任務中曾啟動的 Agent 清單與其行為軌跡。
- FR-043 Agent 行為軌跡應至少包含 Agent 的活動摘要、對話內容、工具呼叫與階段性輸出。

## 風險與限制

- 大型專案的分析成本、執行時間與資源消耗可能偏高。
- 若追求低互動，系統必須清楚定義預設行為與失敗處理策略。
- Server Mode 的 API 穩定性與相容性將直接影響第三方整合體驗。
- 規則文件若僅以 Markdown 撰寫，需明確定義格式與語意，否則可能導致執行結果不一致。
- 規則數量增加後，規則衝突、重複檢查與報告整併策略需要額外設計。
- 若每條規則都啟動獨立 sub-agent，需處理併發數、成本、共享上下文與結果一致性問題。
- 若規則內容可由使用者自由替換，需限制其作用範圍，避免破壞固定 Prompt 框架的穩定性。
- 若 CLI 與 Server 的設定目錄策略不同，需額外定義搜尋順序、預設路徑與覆蓋規則。
- Server Mode 若長期保留分析結果於資料庫，需考量資料量成長與清理策略。
- 若保留完整 Agent 行為軌跡，需考量資料量、敏感資訊與顯示層級控制。

## 初步產品概念

系統核心可視為一個以規則文件驅動的 Code Review Agent。使用者提供專案原始碼後，系統會掃描規則目錄中的 Markdown 規則文件，依據現有規則自動執行對應分析流程，最後輸出相應的報告。

這個規則文件機制在概念上接近「Code Review Skills」：每一份 Markdown 文件代表一種審查能力或主題。系統會掃描規則目錄中的所有規則文件，並為每份規則建立對應分析流程與報告。

在目前構想中，若規則目錄中存在 `記憶體洩漏.md` 與 `性能.md` 兩份規則文件，系統會建立兩個獨立的 sub-agent 分別執行審查，最後各自產出 `記憶體洩漏-report.md` 與 `性能-report.md`。

Review Agent 本身會有固定的 Prompt 框架，規則文件不是完整 Prompt，而是可由使用者替換的規則內容片段。系統執行時會將規則內容整合進固定框架，再交由對應的 Agent 執行分析。

目前規則文件的初步方向可先採用簡單的 Markdown 條列規則，讓使用者容易撰寫與替換。此方向適合作為早期版本的基礎；若未來發現規則管理、解析或一致性不足，再考慮加入少量結構化欄位。

系統需要一個明確的設定根目錄，用於存放共用設定與規則。例如：

```text
appsettings.json
rules/
  記憶體洩漏.md
  性能.md
```

其中 `appsettings.json` 用於設定推理提供商等系統參數，`rules/` 目錄則用於存放可由使用者維護的 Review 規則文件。

初步方向上，Server Mode 預設將這些檔案放在應用程式子目錄中的固定資料夾；CLI 模式則預設使用者家目錄下的專用資料夾，以符合本機工具的使用慣例。

CLI 模式除了預設位置外，也應允許透過參數或環境變數覆寫設定根目錄，以支援 CI、測試環境或多組配置切換。

CLI 也應提供初始化能力，讓使用者可透過額外參數在預設家目錄位置自動建立設定檔、規則目錄與基本規則範本。

CLI 預設設定根目錄在概念上可採用下列位置：

- Windows CLI：`%USERPROFILE%\\.codesnifferdog\\`
- Linux/macOS CLI：`~/.codesnifferdog/`

推理提供商目前以 OpenAI 相容協定為主，至少涵蓋：

- OpenAI
- Azure OpenAI
- 本地部署提供商，例如 `vllm`、`sglang` 與其他 OpenAI 相容 LLM 服務

`appsettings.json` 的具體欄位內容目前不在需求階段完全定義，原則上應保留彈性，於設計與實作階段依實際需要決定。

Server Mode 的 intake 與 queue 第一版可先採用下列落地方式：

- 使用者上傳 ZIP 後，系統先將原始 ZIP 暫存到 server 執行檔目錄下的暫存資料夾。
- 暫存資料夾下第一版至少包含兩個子資料夾：
  - `uploads/`：存放使用者上傳的原始 ZIP，檔名以資料庫中的 `ProjectId` 命名，格式為 `{ProjectId}.zip`。
  - `extracted/`：在分析開始時，暫時存放解壓後的專案內容。
- 系統同時在資料庫建立對應的 project 記錄，作為後續 worker 處理與 UI 查詢的主資料來源。
- queue 第一版可先透過資料庫中的 `status` 與 queue timestamp 推導，不強制一開始就引入獨立訊息佇列基礎設施。

執行產物的保留策略初步如下：

- CLI 模式在任務完成後只保留最終報告，不保留中間產物。
- Server Mode 在分析完成後刪除使用者上傳的 ZIP 檔與解壓內容。
- Server Mode 的報告下載檔不長期落地保存，而是在使用者發出請求時，從資料庫中的結果動態匯出為 ZIP。
- Server Mode 的分析過程與結果需保留於資料庫中，以支援 UI 同步、檢視與複查，直到使用者主動刪除。
- CLI 模式不要求保留失敗任務的複查資料。

Server Mode 需具備 worker、queue 與 project 上限控制機制，以確保多任務情境下的穩定處理能力。系統也需支援使用者在任務完成前主動刪除 project。

Task 狀態在需求層至少應涵蓋 `queued`、`reviewing`、`completed`、`failed` 與 `canceled`，以反映排隊、執行中、完成、失敗與使用者中止等主要情境。

`Delete` 在需求上應視為動作，而不是狀態。使用者執行刪除後，系統應直接刪除該 project 的資料庫資料與相關暫存內容，而不是再保留一筆 `deleted` 狀態的 project。

可觀測性方面，CLI 與 Server Mode 都應讓使用者看到任務當前進度，以及本次任務中啟動過哪些 Agent、各自進行過哪些活動、產生過哪些訊息、呼叫過哪些工具與輸出過哪些結果。

## 需求原則

- Prompt 框架由系統維護，規則內容由使用者維護。
- 使用者可透過修改、增加或刪除規則文件來調整 Review 範圍，但不應直接影響 Agent 的核心角色、流程控制與輸出框架。
- 第一版優先追求規則撰寫與替換的簡單性，再逐步補強規則的結構化能力。
- 設定檔與規則檔應放在可預期的位置，讓使用者能直接管理與備份。
- 暫存輸入應盡快清理，長期保留應以必要的結果資料為主，而非原始專案檔案。
- 系統的自動化程度不能犧牲可觀測性；使用者仍需能追蹤 Agent 的決策與執行軌跡。
